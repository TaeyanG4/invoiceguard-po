# 10. 시연·포트폴리오 작성 가이드

## 1. 제목

**InvoiceGuard-PO: 소형 VLM 기반 인보이스 추출과 발주 대사 검수 지원**

부제: 공개 영어 **합성 인보이스·업무문서**와 자체 합성 발주–인보이스를 구분해 검증한, RunPod 기반 파인튜닝·GPU 서빙 실험.

## 2. 시연 순서

### 장면 A — 정상 문서

독립 PO를 등록하고 합성 인보이스 이미지에 대해 실제 모델을 호출한다. 품번의 앞자리 0과 행 수를 확인한다. 규칙에서 차이를 찾지 못했더라도 `일치 후보`로만 표시한다. 사람 승인 후 export가 활성화되는 것을 보여 준다.

### 장면 B — 실제 거래 차이

PO의 단가 2.50, 이미지의 단가 2.75인 사례를 올린다. AI가 올바르게 읽었다면 차이 검출은 모델 실패가 아니라 업무 목적을 달성한 것이다. 25.00 USD의 참고 차이를 보여 주고, 실제 계약 변경 확인 사유를 남겨 승인한다. 인보이스 값을 PO 값으로 바꾸지 않았음을 설명한다.

### 장면 C — 불확실한 입력과 회귀

`2 cartons / 100 pcs` 또는 읽기 어려운 품번을 보여 주고, 무리한 수량 확정 대신 검수를 요구하는 것을 보여 준다. 관련 dev 실패 사례와 개선 전후의 동일 평가를 설명한다.

실제 모델이 특정 사례를 실패하면 그 실패를 숨기지 않는다. fixture로 UI 흐름만 보여 주는 별도 장면은 화면에 `FIXTURE_DEMO`를 크게 표시한다. 원문 예측을 재생하는 cached replay도 live inference와 구분한다.

## 3. 1페이지 포트폴리오 구조

문제 → 가상 업무/지원범위 → 공개 합성·자체 합성 데이터 구분 → 학습 전후 비교 → 오류 개선 → 서빙 측정 → 한계 순서로 작성한다. 사용자 수/사업 효과를 만들어내지 않는다.

표에는 `M0`, `M1`, 데이터명, 문서 수, 필드 수, 모델/데이터 revision, GPU, p50/p95, 오류 수를 적는다. 미측정 칸은 비워두지 말고 `미측정`으로 표시한다. 실제 프로젝트 결과가 아직 없으므로 현재 문서에는 개선률을 쓰지 않는다.

## 4. 면접에서 설명할 핵심

- “문서 추출 전에 PO를 넣으면 답을 복사할 수 있어, 추출과 대사를 분리했습니다.”
- “공개 영어 InvoiceOCR-Synth에는 SKU 라벨이 없어 임의로 만들지 않았고, 품질 변형은 같은 데이터 분할에 고정했습니다.”
- “가격 변경을 정확하게 추출한 경우와 모델이 숫자를 잘못 읽은 경우를 따로 평가했습니다.”
- “JSON validity와 숫자 정확도를 분리했고, 모델 실패도 전체 분모에 포함했습니다.”
- “QLoRA 학습과 serving quantization은 다른 실험이므로 따로 기록했습니다.”
- “양식 홀드아웃을 사용했지만 합성 문서이므로 실제 통관 정확도로 주장하지 않았습니다.”

이 문장들은 해당 설계를 실제로 구현/검증한 뒤에만 완료형으로 사용한다.

## 5. 이력서 문장 템플릿

> 공개 영어 합성 InvoiceOCR-Synth와 별도 자체 영어 합성 인보이스–발주서 데이터를 구분하여 소형 VLM의 구조화 추출을 학습·평가하고, 독립 PO 대사 및 사람 승인 워크플로를 구현했습니다. [데이터/표본 수], [실제 측정 지표], [GPU/지연]는 재현 가능한 실행 로그로 제공합니다.

아직 구현하지 않았다면 “구현 중” 또는 “기획/설계”로 표기한다. 실제 상업송장 데이터와 현장 사용자 실증이 없다는 점을 한계에 명시한다.
