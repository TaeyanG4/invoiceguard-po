**현재는 근거 있는 독립 평가를 완료할 수 없습니다.** 읽기 명령이 실행되기 전에 도구에서 `code-mode host is disabled` 오류가 반복됐습니다. README를 포함해 저장소 파일을 하나도 읽지 못했습니다.

따라서 **100점 평가, 탈락 수준의 공백, P1–P10의 우선순위·가산점, README 과장 여부는 판정 보류**입니다. 특히 과장이 “없음”이라는 뜻은 아닙니다. 파일을 확인하지 않고 점수나 줄 번호를 붙이면 요청하신 독립 평가의 취지를 훼손합니다.

다만 제공하신 수치에 대해서는 다음과 같은 **검증 전 가설**을 제시할 수 있습니다.

- **0.960 → 0.849는 11.1%p 하락**입니다. HF NF4와 vLLM의 비교는 프레임워크와 정밀도가 함께 달라져, 현재 정보만으로 원인을 특정할 수 없습니다.
- **QLoRA의 학습·추론 조건 차이**는 유력한 점검 대상입니다. NF4 베이스에서 학습한 어댑터를 BF16 베이스에 적용하면 학습 때와 계산 조건이 달라집니다. 다만 이 사실만으로 하락 폭 전체를 설명할 수는 없습니다. 어댑터 로딩·적용 범위와 병합 방식도 확인해야 합니다.
- **이미지 전처리, 채팅 템플릿, 생성 설정**도 동등하게 중요합니다. 이미지 크기·비전 토큰 수, 특수 토큰, 출력 길이 제한, 종료 조건, JSON 파싱 차이는 필드 정확도를 떨어뜨릴 수 있습니다.
- **A40은 BF16을 지원합니다.** “A40이라 BF16 정확도가 낮다”는 설명에는 추가 증거가 필요합니다. BF16과 FP16은 수치 특성이 달라 출력이 달라질 수 있지만, FP32가 반드시 추출 정확도까지 높이지는 않습니다. Linux 자체보다는 함께 달라진 CUDA·PyTorch·attention 커널·라이브러리 버전을 먼저 확인하는 편이 타당합니다.

설명하신 **P3가 기본 모델의 HF 정밀도 비교라면**, 기본 모델이 정밀도 변화에 민감한지는 확인할 수 있습니다. 하지만 그것만으로는 **QLoRA 어댑터와 정밀도의 상호작용**, **HF와 vLLM의 차이**까지 분리하지 못합니다. E1–E5의 실제 내용은 읽지 못했으므로 설계의 충분성은 판단할 수 없습니다.

원인을 가르려면 같은 평가 샘플에서 다음 비교가 필요합니다.

1. **HF 안에서 정밀도 비교:** 기본 모델과 어댑터 적용 모델 각각 NF4/BF16/FP16 비교. FP32는 우선 소수의 실패 샘플로 확인.
2. **같은 정밀도에서 프레임워크 비교:** HF BF16 ↔ vLLM BF16, 어댑터 적용 상태와 입력·생성 조건 고정.
3. **샘플별 실패 분해:** 원문 생성 결과를 보존해 추출 오답, 출력 잘림, 형식·파싱 실패를 구분.

이 비교가 갖춰지면 추가 GPU 비용을 쓰기 전에 원인 범위를 상당히 좁힐 수 있습니다. 요청하신 최종 평가를 진행하려면 **읽기 도구가 정상 동작하는 세션에서 저장소 검토를 재개해야 합니다.**
